## Findings

- `code3.cu` and `code_old.cu` have the same CTA tile size `128 x 128`, so their DRAM arithmetic intensity is essentially the same: about `16 FLOP/byte` for the tiled GEMM path.
- Including the final `C` store changes the number only slightly, to about `15.97 FLOP/byte`.
- `code_old.cu` compiles with `255 registers/thread` and `65536 bytes smem`; `code3.cu` compiles with `252 registers/thread` and `32768 bytes smem`.
- With `256 threads/block`, both versions are still register-limited to roughly one resident block per SM, so occupancy stays around `8 warps/SM` or `12.5%` on SM80.
- The current Nsight report `report3.nsys-rep` is for `./main3`; the kernel summary shows `9.623 s` total kernel time for one `matmul_kernel` launch.
- The lack of a clear Tensor Core speedup is consistent with low occupancy, no load/compute double-buffering, and high fragment/register pressure; the kernel stays compute-bound, but it does not reach a much higher compute roof.
- `main3`'s SASS contains many `DMMA.884` instructions, while the `code_old.cu` build shows `DFMA`-heavy scalar FP64 code, so `code3.cu` does map to Tensor Core execution at the machine-code level.
